## 一、本项目（个人 AI 助手 Agent）技术细节

### Q：你这个个人 AI 助手，技术架构是怎样的？
我自己从零搭的一套 RAG Agent 系统，不是调个 API 就完事。
整体链路是：用户提问 → Query 改写（多轮指代消解）→ 混合检索（稠密向量 + BM25 双路召回，RRF 融合）→ 相关性判定（不可靠就拒答）→ 生成 → 引用溯源。
编排用 LangGraph 的 StateGraph 把这几个节点串起来，每个节点都能单独关掉或替换，且检索链路节点（改写/检索/判定）事件流可观测。前端是 FastAPI 做 SSE 流式对话，加一个零构建的前端页面。向量库用 Qdrant，开发期嵌入式、部署切服务端；会话级多轮记忆（滑动窗口+摘要）保证跨轮上下文一致性。

### Q：为什么用混合检索，而不是单纯向量检索？
因为单纯向量检索有两个硬伤。一是**专有名词/缩写召回差**——比如"叫号系统""BM25"这种词，向量模型容易把它们语义模糊掉；二是**关键词精确匹配场景**向量不擅长。
所以我加了 BM25 稀疏召回补这一块，和稠密向量各取所长，最后用 RRF（Reciprocal Rank Fusion）融合。我自己的离线评测里，加稀疏之后 MDD（MRR）反而从 0.806 掉到 0.794。我查了原因，是我这个语料太短、稠密向量已经覆盖住了语义，BM25 反而引入噪声。所以我的结论不是"混合检索一定更好"，而是"要看语料规模"。

### Q：切片（chunking）你是怎么设计的？
不同文档类型用不同的块大小，不能一刀切。
- 问答对（qa）整块保留，2000 字上限——因为问答是语义完整的，切断上下文就丢了；
- 项目文档（projects）700 字，允许稍微大一点保留项目背景；
- 个人档案（profile）500 字，按标题层级切；
- 笔记/JD 600 字。
块之间留 80 字重叠，避免一句话被切断后首尾信息丢失。这个策略也是我在评测里验证过的：切太碎召回噪声大，切太大精度掉，折中在这附近。

### Q：多轮对话你怎么处理的？
两个机制，均为**会话级记忆**。一是**滑动窗口 + 摘要压缩**：短期保留最近几轮，超出预算就把早期的对话做摘要压进上下文，避免 token 爆掉。二是**Query 改写**：多轮里最常见的坑是"那他第二段实习呢"这种只有代词没有实体的追问，直接拿去检索必然错。我做了指代消解，把"他"补全成主体姓名、把"那段"补全成项目名，再送检索。这一环和多轮记忆是配套的一一没有改写，多轮记忆基本是摆设。

### Q：怎么保证回答不乱编？
两道防线。第一道是**相关性判定**：检索结果和 query 的词面重叠度太低（扣除姓名后几乎没有实质命中），就判定知识库里没依据，直接走拒答分支，坦诚说"这个我暂时没有可靠信息"，而不是硬编。第二道是**引用溯源**：每条回答都标注来源片段，面试官能点开看原文。真要生成时，prompt 里明确写了"只基于参考资料回答，不编造库外信息"。

### Q：你做了效果评测吗？量化数据是多少？
做了，而且这是我刻意要的——光说"用了 RAG"在面试里没说服力。
我自建了 14 条 query 的评测集（12 条可召回 + 2 条拒答类），用确定性的 Recall@K、MRR、R@1 做消融对比：
- 仅稠密向量：R@1 = 75.0%，Recall@5 = 91.7%，MRR = 0.806
- 加 BM25 稀疏（RRF 融合）：R@1 = 75.0%，Recall@5 = 91.7%，MRR = 0.794
- 完整（+Cross-Encoder 重排）：同上（当前部署包未内置重排模型，链路降级为 RRF）

**这里有个我踩过的坑，也是我想讲的点**：加了稀疏路之后 MRR 反而从 0.806 掉到 0.794。我一开始以为实现错了，排查后确认是**这个语料本身的问题**——项目文档篇幅短、语义集中，稠密向量已经覆盖住了，BM25 引来的词面匹配反而在少量样本上引入了噪声。所以我的结论不是"混合检索一定更好"，而是：**在这个语料规模下，稠密单路就够了；混合检索的价值要等文档量上去才体现**。据此我把重排链路保留在架构里但默认关闭，不为"指标好看"引入无效复杂度。

这套评测脚本是离线跑的，改了切片或检索策略能立刻复测前后对比。我觉得比"我做了混合检索"更有说服力的，是我能说清**什么情况下它不work**。

### Q：为什么选 Qdrant 而不是 Milvus 或 pgvector？
三个都了解过，选 Qdrant 是权衡部署成本和场景。
- pgvector 胜在和 Postgres 一体、事务方便，但我这场景不需要关系建模，单独引 Postgres 反而重；
- Milvus 分布式和海量向量强，但部署重、本地资源占用高，我一个人做项目没必要；
- Qdrant 轻量、Docker 一行起、原生支持稠密+稀疏双向量和 payload 过滤，正好对上我的混合检索需求。如果以后真要上亿级向量，我会 reconsider Milvus，但现阶段 Qdrant 是最优解。

### Q：LangGraph 你用下来感觉怎么样，值得吗？
值得，但要看场景。它最大的价值是把"流程"显式建模成图——改写、检索、判定、生成每个节点独立、可观测、可插拔。比如我要加一个"是否需要联网"的分支，加个节点和一条条件边就行，不用改一大坨 if-else。
代价是学习成本和一点点性能开销，对对话这种低 QPS 场景完全可接受。如果是超轻量的单链调用，手写也行，但我这项目节点多、还要条件分支（可靠/不可靠走不同路），LangGraph 明显更清晰。

## 二、数字员工平台（公司项目）技术细节

### Q：你之前做的"多模型数字员工 Agent 平台"具体是什么？
是公司的一个内部项目，目标是用 Agent 把多个垂直业务系统（CRM、工单、知识库等）串起来，让一个"数字员工"通过自然语言完成跨系统操作。
技术上是 RAG 检索公司制度/产品文档 + Function Calling 调业务接口 + 上下文管理维持多轮对话 + FastAPI 对外服务 + Docker 部署。和我现在的个人项目技术栈高度重合。

### Q：那个平台和你现在这个项目有什么关系？
正好是我做这个个人项目的**动机来源**。在那个公司项目里我发现 RAG 效果时好时坏，但定位不到问题出在哪——没有评测、没有量化。
所以我自己从零做了一版可评测的实现：把检索拆成混合检索、加了重排、做了离线评测脚本，用数据证明每一步改进。等于把公司项目里"想做但没做完/没验证"的部分，独立做成了一个完整闭环。这样简历上不是两个雷同项目，而是一条清晰的"发现问题→独立解决→用数据证明"的叙事。

### Q：那个平台做到什么程度了？
实话说只做了一半，没完全收尾——这也是我把它在简历上压低、把个人项目顶上去的原因。
已落地的是 RAG 基础链路、Function Calling 框架、FastAPI 服务和 Docker 部署；缺的是效果评测、检索策略优化、以及足够的业务接入。我现在的方向是先把个人这个项目做扎实、有量化成果，再回头把公司项目补完——那时它就能写成真实交付，而不是"参与过"。

## 三、RAG / AI 高频八股题

### Q：RAG 和微调（finetuning）怎么选？
看目标和成本。RAG 适合**知识频繁更新、要可追溯、要低成本**的场景——知识存在外面，更新文档就行，不用重训。微调适合**固定风格/固定能力、要模型"学会某种能力"**的场景，但训练贵、知识更新慢、不可解释。
我的项目知识是简历内容，会随我补充而变，且面试官要能溯源，所以 RAG 是天然选择。真实落地里常常是"RAG 打底 + 轻量微调做风格/格式"的组合。

### Q：RRF 融合是什么，为什么用它而不是简单加权？
RRF（Reciprocal Rank Fusion）是把多路召回的结果按排名倒数求和再排序：score = Σ 1/(k+rank)。
它最大的好处是**不用调权重、不要求各路分数同尺度**。稠密向量的相似度和 BM25 的词频分根本不在一个量纲，直接加权要反复调参；RRF 只看排名，绕开了量纲问题，鲁棒性高。k 一般取 60。我项目里稠密和稀疏就是靠它融合的。

### Q：Embedding 模型你怎么选的？
开发期用 BAAI/bge-small-zh-v1.5（512 维，约 100MB），中文检索质量够用、下载快、本地跑得动。
生产档我预留了 jina-embeddings-v3（1024 维）作为升级选项——它内部用 task_id 区分"查询"和"文档"两种编码任务，中文多语言表现更好，代价是 2.3GB、对部署机器要求高。选型上我遵循"开发用轻量快速迭代、上线再上重模型"的思路，一行配置切换，代码无感。

### Q：怎么判断 RAG 系统"够好"？
不能只看"能回答"。我从三个角度：一是**检索质量**，用 Recall@K / MRR 这类确定性指标，配消融对比看每一步贡献；二是**生成质量**，用答案相关性、是否有依据、是否编造来评估（RAGAS 的思路）；三是**线上行为**，拒答率是否合理、引用是否准确。
关键是要有**可复现的评测集**——我建了 14 条 query（12 条可召回 + 2 条拒答类）带标准答案，改任何策略都能立刻跑出前后对比。没有评测的 RAG 优化都是瞎调。

### Q：知识库里没有答案时，你怎么办？
绝不硬编。这是 RAG 可信度的底线。
我的处理是：相关性判定发现检索结果和 query 实质不匹配（扣除姓名后几乎没有词面重叠），就走拒答分支，明确告诉用户"这个我暂时没有可靠信息"。同时 prompt 约束生成阶段只基于检索内容。宁可说"不知道"，也比编一个看起来对、实际错的答案强——后者在面试场景尤其致命。
